# JavaScript

Применяй к `.js` и JavaScript-частям `.jsx`. Для `.ts` и `.tsx` сначала примени этот референс, затем TypeScript-правила.

## Строки и формат

- Используй одинарные кавычки. Template literals нужны для интерполяции или многострочного текста.
- По умолчанию не ставь semicolon и trailing comma, но formatter, linter и локальный стиль имеют приоритет.
- Короткие объекты, массивы и вызовы оставляй в одну строку.
- В многострочной форме размещай свойства, элементы и аргументы по одному на строке.

## Ранние возвраты (Early Return) и ветвление

- Используй ранние возвраты для отсутствующих данных, ошибок, запрещённых состояний и других guard conditions.
- Сначала обрабатывай исключающие условия, затем размещай основной сценарий функции.
- Не добавляй `else` после ветки с безусловным `return` или `throw`.
- Не оборачивай основной сценарий в несколько уровней `if`, если вложенность можно заменить guard clauses.
- Не добавляй ранние возвраты механически, если линейное условие читается проще.

Хорошо:

```js
/**
 * Возвращает отображаемое имя пользователя.
 *
 * Учитывает отсутствие пользователя и его неактивное состояние.
 */
const getName = (user) => {
  if (!user) {
    return 'Гость'
  }

  if (!user.isActive) {
    return 'Неактивный пользователь'
  }

  return user.name
}
```

Плохо:

```js
/**
 * Возвращает отображаемое имя пользователя.
 *
 * Учитывает отсутствие пользователя и его неактивное состояние.
 */
const getName = (user) => {
  if (user) {
    if (user.isActive) {
      return user.name
    } else {
      return 'Неактивный пользователь'
    }
  } else {
    return 'Гость'
  }
}
```

## Именование значений

- Массивы называй во множественном числе.
- Списки идентификаторов называй `*Ids`.
- Словари и maps называй `*ById`, `*Map` или `*Dict`.
- Boolean-значения начинай с `is`, `has`, `can` или `should`.
- Внутренние обработчики называй `handle*`, callback-параметры и свойства — `on*`.

```js
const userIds = ['u1', 'u2']
const usersById = {}
const isReady = true

/**
 * Обрабатывает отправку формы.
 *
 * Запускает сценарий сохранения подготовленных данных.
 */
const handleSubmit = () => {
  // ...
}
```

## Константы и стабильные значения

- Переиспользуемую константу верхнего уровня называй в `SCREAMING_SNAKE_CASE`.
- Обычную локальную переменную, объявленную через `const`, называй в `camelCase`.
- Связанный набор стабильных runtime-значений группируй в константный объект.
- Ключи enum-like объекта называй в `SCREAMING_SNAKE_CASE`.
- Значения сохраняют формат runtime-контракта и не обязаны быть в uppercase.
- Не переименовывай непрозрачные значения внешнего API ради code style.
- Если проекту нужны собственные внутренние значения, сопоставляй внешний контракт с ними на границе владельца.
- Если объект должен быть неизменяемым в runtime, явно зафиксируй его через `Object.freeze`.

```js
export const MAX_PAGE_SIZE = 100

export const PAYMENT_STATUS = Object.freeze({
  PENDING: 'pending',
  PAID: 'paid',
  FAILED: 'failed'
})

const currentPage = 1
```

## Imports и exports

- Используй пробелы в named imports: `import { createUser } from './create-user'`.
- Для собственного кода предпочитай named exports.
- Default export используй только по требованию framework, tooling или локального стандарта.
- Namespace imports применяй только когда этого требует API библиотеки или локальный стандарт.
- Не создавай barrel и не обходи public API без понимания архитектурной границы.
- Не меняй порядок и пути imports только ради вкусового форматирования.

## JavaScript-данные

- Проверяй внешние данные до использования, даже если источник считается стабильным.
- Не смешивай отсутствие значения с falsy-значениями: учитывай, что `0`, `false` и `''` могут быть валидными.
- Не используй truthy-проверку, если контракт требует различать `null`, `undefined` и другие falsy-значения.
- Повторяющуюся проверку формы данных выноси в именованный predicate.

## JSDoc

Документируй назначение сущности, а не синтаксис реализации.

- Каждая именованная JS/TS-функция и каждый класс имеют многострочный JSDoc непосредственно перед объявлением.
- Правило функций распространяется на function declarations, именованные function expressions, arrow functions в именованной переменной, handlers и custom hooks.
- Описывай назначение функции и только тот контекст, который нужен для понимания её поведения.
- Используй одну или несколько строк и абзацев в зависимости от сложности функции; фиксированного шаблона и длины нет.
- Добавляй механику, важные нюансы, ограничения и результат только когда они неочевидны из имени и сигнатуры.
- Для чистого JavaScript описывай через JSDoc важные параметры, возвращаемые значения и контракт данных, если это не выражено иными средствами проекта.
- Не документируй обычные локальные переменные и inline callbacks.
- Если inline callback требует объяснения, вынеси его в именованную функцию.
- React-компоненты документируй по правилам JSX/TSX.

Для простой функции достаточно краткого описания:

```js
/**
 * Возвращает отображаемое имя пользователя.
 */
const getDisplayName = (user) => user.name
```

Для сложной функции добавляй необходимый контекст:

```js
/**
 * Собирает дерево категорий из плоского списка.
 *
 * Категории без родителя попадают в корень дерева.
 *
 * @param {Category[]} categories Плоский список категорий.
 * @returns {CategoryNode[]} Дерево категорий.
 */
export const buildCategoryTree = (categories) => {
  // ...
}
```

## Проверка

- Строки, collections, вызовы, semicolon и trailing comma соответствуют инструментам проекта.
- Ранние возвраты обрабатывают guard conditions до основного сценария и не создают лишний `else`.
- Boolean-значения, handlers и callbacks названы по роли.
- Константы верхнего уровня, локальные `const` и enum-like наборы названы по своей роли.
- Imports и exports не нарушают public API.
- Внешние данные проверяются до использования.
- JSDoc именованных функций содержит достаточный для понимания поведения контекст без обязательного шаблона.
- Классы документированы на точке объявления.
